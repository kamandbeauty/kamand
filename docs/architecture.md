## ۱. چرا این معماری؟

هر تصمیم معماری در جاوید پاسخی به یک مشکل مشاهده‌شده در محصولات رقیب است:

| مشاهده در بازار | تصمیم معماری |
|---|---|
| کاربر با پایان اشتراک به دفتر حسابش دسترسی نداشت | ماژول جداگانهٔ `subscription.ts` با فهرست سفید صریح |
| قطعی اینترنت فروش را متوقف می‌کرد | UUID سمت کلاینت + صف تغییرات + ساعت لامپورت |
| چندپلتفرمی شدن به بازنویسی و افت کیفیت انجامید | پکیج `core` بدون هیچ import از DOM یا React |
| گزارش‌ها با واقعیت ناهماهنگ می‌شدند | هیچ جدول تجمیعی ذخیره نمی‌شود |

## ۳. موتور سند دوطرفه

قاعدهٔ تخطی‌ناپذیر: **جمع بدهکار = جمع بستانکار**.

`EntryBuilder` تنها راه ساخت سند است و پیش از تحویل، توازن را بررسی می‌کند:

```ts
const b = new EntryBuilder(bizId, date, 'فروش', 'invoice', invId);
b.debit(receivableId, 1_100_000, { partyId });
b.credit(salesId, 1_000_000);
b.credit(vatPayableId, 100_000);
const entry = b.build(uuid(), now);  // اگر نامتوازن باشد پرتاب می‌کند
```

رفتارهای محافظتی:
- مبلغ صفر → ردیف اضافه نمی‌شود
- مبلغ منفی → خودکار به سمت مقابل منتقل می‌شود
- ردیف با بدهکار و بستانکار هم‌زمان → خطا
- سند تک‌ردیفی → خطا

### الگوهای ثبت

| رویداد | بدهکار | بستانکار |
|---|---|---|
| فروش | دریافتنی | فروش + مالیات فروش |
| بهای فروش | بهای تمام‌شده | موجودی کالا |
| خرید | موجودی + مالیات خرید | پرداختنی |
| برگشت از فروش | برگشت از فروش + مالیات | دریافتنی |
| ↳ بازگشت کالا | موجودی کالا | بهای تمام‌شده |
| دریافت وجه | صندوق/بانک | دریافتنی |
| ثبت چک دریافتی | اسناد دریافتنی | دریافتنی |
| وصول چک | بانک | اسناد دریافتنی |

## ۴. موتور بهای تمام‌شده

سه روش پشتیبانی می‌شود و در سطح کسب‌وکار تنظیم می‌گردد.

```ts
const state = replayProduct(movements, 'fifo');
const { cogs, remaining } = consumeStock(state.layers, 12, 'fifo');
```

- **FIFO** — از قدیمی‌ترین لایه مصرف می‌کند
- **LIFO** — از جدیدترین لایه
- **میانگین موزون** — لایه‌ها در هر ورود ادغام می‌شوند

### ⚠️ تلهٔ برگشت از فروش

باگی که در توسعهٔ جاوید کشف و رفع شد:

> کالای برگشتی باید با **بهای تمام‌شده** به انبار بازگردد، نه با **قیمت فروش**.

اگر با قیمت فروش برگردد، هم ارزش انبار و هم سود دوره متورم می‌شود. مثال:

```
خرید ۱۰۰ عدد × ۱۰٬۰۰۰  →  انبار: ۱٬۰۰۰٬۰۰۰
فروش ۱۲۰ عدد × ۱۵٬۰۰۰  →  بهای فروش: ۱٬۲۴۰٬۰۰۰
برگشت ۲۰ عدد:
  ❌ غلط: انبار +۳۰۰٬۰۰۰ (قیمت فروش)  →  سود متورم
  ✅ درست: انبار +۲۰۰٬۰۰۰ (بهای اصلی) →  سود واقعی
```

`createReturn()` بهای تمام‌شده را به نسبت مقدار برگشتی از فاکتور اصلی منتقل
می‌کند و `invoiceLineUnitCost()` تضمین می‌کند حرکت انبار با بهای درست ثبت شود.
آزمون شمارهٔ ۵ در `scenario.test.ts` این را قفل می‌کند.

## ۱۱. سامانهٔ مؤدیان

بزرگ‌ترین شکاف رقبای موبایلی: آن‌ها «فاکتور رسمی» صادر می‌کنند ولی از نظر
مالیاتی رسمی نیست، چون شمارهٔ منحصربه‌فرد مالیاتی ندارد.

### شمارهٔ منحصربه‌فرد مالیاتی

ساختار ثابت ۲۲ کاراکتری:

```
 A1D2E3   050B7   00000000FF   4
 └──┬──┘  └─┬─┘   └────┬────┘   │
   ۶        ۵          ۱۰       ۱
 حافظه    تاریخ      سریال   کنترلی
          (Hex)      (Hex)  (Verhoeff)
```

- **شناسهٔ حافظه** — از کارپوشه دریافت می‌شود. الفبای مجاز حروف I، J، L، Q، V
  و رقم ۰ را به دلیل شباهت بصری ندارد.
- **تاریخ** — تعداد روز سپری‌شده از ۱۹۷۰/۰۱/۰۱ به مبنای ۱۶.
- **سریال** — شمارندهٔ داخلی حافظه، به مبنای ۱۶.
- **رقم کنترلی** — الگوریتم Verhoeff.

### چرا Verhoeff؟

برخلاف Luhn، الگوریتم Verhoeff **همهٔ** خطاهای تک‌رقمی و همهٔ جابه‌جایی‌های
ارقام مجاور را می‌گیرد. پیاده‌سازی بر پایهٔ گروه دووجهی D5 است و با
بردارهای آزمون استاندارد تأیید شده:

```ts
verhoeffCheckDigit('236')          // 3
verhoeffCheckDigit('12345')        // 1
verhoeffCheckDigit('142857')       // 0
```

آزمون‌ها به صورت جامع همهٔ تغییرات تک‌رقمی و جابه‌جایی‌های ممکن را بررسی
می‌کنند، نه فقط چند نمونه.

### نسخه‌پذیری

الگوها و اقلام اطلاعاتی توسط سازمان امور مالیاتی بروزرسانی می‌شوند. به همین
دلیل `TAX_SPEC_VERSION` در خروجی هر صورتحساب درج می‌شود و ساختار به صورت
آداپتور نوشته شده تا تغییر دستورالعمل به بازنویسی منجر نشود.

## ۱۲. چاپ حرارتی و فارسی

چاپگرهای حرارتی معمولاً یونیکد کامل ندارند و مهم‌تر: **حروف فارسی را
نمی‌چسبانند**. دو مرحله لازم است:

**۱ — شکل‌دهی.** هر حرف بسته به همسایه‌هایش یکی از چهار شکل منفرد، آغازین،
میانی یا پایانی را می‌گیرد. حروفی مثل «د»، «ر»، «و» به حرف بعدی نمی‌چسبند.
ترکیب «لا» هم باید به یک نویسهٔ واحد تبدیل شود.

```
سلام  →  ﺱ + ﻼ + ﻡ   (لام‌الف ترکیب شد: ۴ حرف → ۳ نویسه)
در    →  ﺩ + ﺭ        (د نمی‌چسبد، هر دو منفرد)
```

**۲ — معکوس‌سازی.** چاپگر از چپ می‌چیند، پس متن راست‌به‌چپ باید از پیش
معکوس شود — ولی قطعه‌های لاتین و عددی داخل متن نباید معکوس شوند.

### مسیرهای چاپ

بلوتوث (Web Bluetooth) → USB (Web Serial) → دانلود فایل.

مسیر سوم همیشه در دسترس است تا نبود پشتیبانی مرورگر کاربر را بن‌بست نکند —
همان اصل «هرگز کاربر را در بن‌بست نگذار» که در تعهد اول هم دیدیم.

## ۱۳. ذخیره‌سازی

زنجیرهٔ سقوط: **IndexedDB → localStorage → حافظهٔ موقت**.

localStorage سقف حدوداً ۵ مگابایتی دارد و همزمان است؛ مغازه‌ای با چند هزار
فاکتور از آن عبور می‌کند. IndexedDB نامحدودتر و ناهمزمان است.

نوشتن‌های پیاپی با تأخیر ۲۵۰ میلی‌ثانیه فشرده می‌شوند تا تایپ کاربر ده‌ها
نوشتن روی دیسک ایجاد نکند، و `flushDB()` پیش از بستن صفحه یا خروجی گرفتن
نوشتن معلق را قطعی می‌کند.

## ۱۴. مهاجرت داده

درس مستقیم از شکست رقیب: مهاجرت آن‌ها **دستی** بود — کاربر باید درخواست
ثبت می‌کرد و منتظر می‌ماند تا پشتیبانی انجامش دهد. نتیجه: کاربران وسط
مهاجرت به دفتر حسابشان دسترسی نداشتند.

در جاوید `migrate()` هنگام هر بارگذاری اجرا می‌شود، **خودکار و بی‌صدا**،
و idempotent است:

```ts
export function migrate(db: DB): DB {
  const out = { ...db };
  if (!out.taxProfile) out.taxProfile = { ... };
  if (!Array.isArray(out.taxSubmissions)) out.taxSubmissions = [];
  return out;
}
```

قاعده: افزودن فیلد جدید همیشه باید یک شاخهٔ پیش‌فرض در `migrate()` داشته باشد.

## ۱۵. همگام‌سازی چنددستگاهی

### چرا قرارداد در هسته است؟

`packages/core/src/protocol.ts` تنها منبع حقیقت شکل پیام‌هاست و **هر دو**
طرف از آن استفاده می‌کنند. نتیجه: ناسازگاری کلاینت و سرور در زمان کامپایل
گرفته می‌شود، نه وسط فروش روی گوشی مغازه‌دار.

### دفتر فقط-افزودنی

جدول `changes` هرگز بازنویسی یا حذف نمی‌شود:

```sql
CREATE UNIQUE INDEX idx_changes_dedupe ON changes(business_id, id);
CREATE INDEX idx_changes_pull ON changes(business_id, seq);
```

سه دلیل:
1. همگام‌سازی افزایشی به **ترتیب پایدار** نیاز دارد (`seq`)
2. ردّ ممیزی در نرم‌افزار مالی چندکاربره اجباری است
3. حذف هم یک تغییر است (`op = 'delete'`)، پس به دستگاه‌های دیگر منتقل می‌شود

جدول `entity_state` آخرین برندهٔ هر موجودیت را نگه می‌دارد تا حل تعارض
نیازی به بازپخش کل دفتر نداشته باشد.

### سه تضمین

**۱ — Idempotent.** ایندکس یکتای `(business_id, id)` تضمین می‌کند ارسال
مجدد همان تغییر رکورد تکراری نسازد. سرور پاسخ `duplicate` می‌دهد که برای
کلاینت موفقیت است. این حیاتی است: قطعی وسط ارسال یعنی کلاینت دوباره
می‌فرستد و نباید داده دوبرابر شود.

**۲ — حل تعارض قطعی‌گرا.** همان قاعدهٔ کلاینت: ساعت لامپورت → زمان →
شناسهٔ دستگاه. منطق عمداً در `shouldApply()` سرور تکرار شده تا سرور به
کد کلاینت وابسته نباشد، ولی نتیجه دقیقاً یکسان بماند. آزمون «ترتیب رسیدن
روی نتیجهٔ نهایی اثر ندارد» این را قفل می‌کند.

**۳ — اتمی.** `node:sqlite` برخلاف better-sqlite3 کمکِ `transaction()`
ندارد، پس BEGIN/COMMIT/ROLLBACK صریح نوشته شده. یک بستهٔ تغییرات یا کامل
ثبت می‌شود یا هیچ.

### دستگاه تغییرات خودش را نمی‌گیرد

```sql
WHERE business_id = ? AND seq > ? AND device_id != ?
```

هم پهنای باند را کم می‌کند و هم از حلقهٔ بی‌پایان جلوگیری می‌کند.

### احراز هویت

کد یک‌بارمصرف با ملاحظات:
- کد **هرگز خام ذخیره نمی‌شود** — فقط هش SHA-256
- مقایسه با `timingSafeEqual` تا حملهٔ زمانی ممکن نباشد
- محدودیت تلاش (۵) و فاصلهٔ ارسال مجدد (۶۰ ثانیه)

**درسی که تست داد:** محدودیت نرخ اولیه فقط بر اساس IP بود. تست نشان داد
چند کارمند یک مغازه که پشت یک NAT مشترک هستند همدیگر را قفل می‌کنند.
حالا دو سطحی است: سخت‌گیرانه روی هر شماره، سهل‌گیرانه‌تر روی هر IP.

### همگام‌سازی اختیاری است

این یک تصمیم محصولی است، نه فنی. برنامه بدون هیچ سروری کامل کار می‌کند.
اگر کاربر سرور تنظیم نکند، هیچ‌چیز از دست نمی‌رود — که ادامهٔ منطقی
تعهد اول است: دادهٔ کاربر مال خودش است و به هیچ سرویسی گروگان نیست.

## ۱۶. لایهٔ انتقال سامانهٔ مؤدیان

### چه چیزی ساخته شد و چه چیزی نه

| بخش | وضعیت |
|---|---|
| نرمال‌سازی JSON مطابق دستورالعمل | ✅ پیاده و آزمون‌شده |
| امضای RSA-2048-SHA256 | ✅ با کلید عمومی راستی‌آزمایی می‌شود |
| رمزگذاری XOR + AES-256-GCM | ✅ آزمون واقعاً رمزگشایی می‌کند |
| بسته‌بندی کلید با RSA-OAEP-SHA256 | ✅ رفت‌وبرگشت آزمون‌شده |
| کلاینت ارسال و استعلام | ✅ با fetch تزریق‌شدنی |
| گواهی امضا از مرکز میانی | ⛔ نیازمند مراجعه به rca.gov.ir |
| کلید عمومی سازمان | ⛔ از GET_SERVER_INFORMATION |
| اعتبارنامهٔ کارپوشه | ⛔ از سامانهٔ مؤدیان |

سه مورد آخر **اعتبارنامهٔ رسمی** هستند و ساختنی نیستند. بقیه کامل است.

### نرمال‌سازی

قاعدهٔ سازمان دقیقاً این است:

```
{ "k2":"v1", "k4":"v2", "k3":{ "k1":"v4", "k5":"v5" } }
  ↓ مسطح‌سازی با مسیر نقطه‌ای
k2=v1 · k4=v2 · k3.k1=v4 · k3.k5=v5
  ↓ مرتب‌سازی الفبایی کلیدها
k2 · k3.k1 · k3.k5 · k4
  ↓ ادغام با #
v1#v4#v5#v2
```

سه نکتهٔ ظریف که آزمون‌ها قفلشان می‌کنند:
- **آرایه‌ها مرتب نمی‌شوند** — فقط کلیدهای شیء
- `null` و رشتهٔ خالی → `###`
- کاراکتر `#` داخل متن → `##`

### چرا رمزنگاری تزریق‌شدنی است؟

`TaxCrypto` یک واسط است و پیاده‌سازی در `apps/server` قرار دارد. دلیل:
هستهٔ `@javid/core` نباید به `node:crypto` یا Web Crypto وابسته شود،
وگرنه همان مشکل رقیب پیش می‌آید — کدی که فقط روی یک پلتفرم کار می‌کند.

### زنجیرهٔ رمزگذاری

```
JSON صورتحساب
  → XOR با کلید متقارن (بلوک‌های ۳۲ بایتی)
  → AES-256-GCM با IV تصادفی ۱۶ بایتی
  → کلید متقارن با RSA-OAEP-SHA256 و کلید عمومی سازمان بسته‌بندی می‌شود
```

آزمون این زنجیره را **معکوس** طی می‌کند و به JSON اصلی می‌رسد — یعنی
درستی‌اش صرفاً ادعا نیست.

## ۱۷. پیامک

آداپتور با سه پیاده‌سازی: کاوه‌نگار، ملی‌پیامک و وب‌هوک عمومی.

دو تصمیم:

**۱ — پیکربندی ناقص خطا نیست.** اگر `SMS_PROVIDER=kavenegar` باشد ولی

درس کلی: **خروجی تشخیصی همیشه روی stderr**.

## ۱۹. ردّ ممیزی و قفل دورهٔ مالی

هر دو در تحلیل بازار «اجباری در نرم‌افزار مالی چندکاربره» شناخته شدند.

### چرا ردّ ممیزی؟

وقتی چند نفر روی یک دفتر کار می‌کنند، باید بشود فهمید چه کسی چه چیزی را
کِی تغییر داده. بدون آن، اختلاف بین شرکا حل‌نشدنی است.

سه تصمیم طراحی:

**۱ — ویرایش فقط تفاوت را نگه می‌دارد.** ذخیرهٔ کل رکورد در هر ویرایش،
حافظهٔ دستگاه را سریع پر می‌کند. `diffRecords()` فقط فیلدهای تغییرکرده را
نگه می‌دارد و `updatedAt` و `lamport` را نادیده می‌گیرد چون همیشه تغییر
می‌کنند و اطلاعاتی ندارند.

**۲ — فیلدهای حساس پاک می‌شوند.** توکن، رمز و کلید خصوصی حتی در اشیای
تودرتو با `‹حذف‌شده›` جایگزین می‌شوند. ردّ ممیزی نباید خودش نشتی امنیتی باشد.

**۳ — سقف تعداد.** فقط ۲۰۰۰ رویداد اخیر روی دستگاه می‌ماند؛ بقیه در
پشتیبان باقی می‌مانند.

### قفل دورهٔ مالی

وقتی سال مالی بسته و اظهارنامه ارسال شد، ویرایش سند آن دوره یعنی
ناهماهنگی با چیزی که به سازمان اعلام شده.

```ts
guardPeriod(db, invoice.date);  // پیش از هر نوشتن مالی
```

عمداً **پرتاب می‌کند** نه اینکه مقدار برگرداند — فراموش کردن بررسی باید سخت باشد.

بازکردن دوره یک عملیات جداگانه است که **دلیل می‌خواهد** (حداقل ۱۰ نویسه)
و در ردّ ممیزی ثبت می‌شود.

### آزمون واقعی

آزمون سرتاسری در `ssr/render.tsx` قفل را در جریان واقعی ثبت امتحان می‌کند:
یک فاکتور داخل دورهٔ بسته باید `PeriodLockedError` بدهد و فاکتوری با
تاریخ بعد از قفل باید عادی ثبت شود. این یعنی قفل واقعاً وصل است، نه
اینکه فقط تابعش وجود داشته باشد.

## ۲۰. نقش و جداسازی داده

چهار نقش با ۱۴ اجازهٔ دقیق. جدول کامل در `workspace.ts`.

**نکتهٔ مهم:** `report.view` و `export.data` برای **همهٔ** نقش‌ها فعال است،
حتی «فقط مشاهده». این ادامهٔ تعهد اول است: دادهٔ کسب‌وکار نباید پشت نقش هم
قفل شود؛ فقط نوشتن محدود می‌گردد. آزمونی وجود دارد که این را برای هر چهار
نقش بررسی می‌کند.

### جداسازی

```ts
scopeTo(items, businessId)      // فیلتر به یک کسب‌وکار
assertScoped(items, businessId) // تشخیص نشتی
```

`scopeTo` عمداً یک تابع ساده و مشترک است تا هر جای کد که دادهٔ چند
موجودیت را می‌خواند از آن رد شود و فراموش کردن فیلتر سخت‌تر باشد.
`assertScoped` در آزمون‌ها نشتی بین کسب‌وکارها را می‌گیرد — خطرناک‌ترین
باگ ممکن در یک سیستم چنداجاره‌ای.

## ۲۱. بستن سال مالی

نوع سند `closing` از ابتدا در `types.ts` اعلام شده بود ولی پیاده نشده بود.
این شکاف واقعی بود: بدون بستن سال، سود سال گذشته با امسال قاطی می‌شود و
صورت سود و زیان معنی خود را از دست می‌دهد.

### سه سند، به این ترتیب

**۱ — اختتامیه.** همهٔ حساب‌های درآمد و هزینه با قید معکوس صفر می‌شوند و
اختلاف (سود یا زیان دوره) به سود انباشته می‌رود:

```
بدهکار: فروش ۳٬۰۰۰٬۰۰۰
  بستانکار: بهای تمام‌شده ۱٬۸۰۰٬۰۰۰
  بستانکار: هزینه‌ها ۵۰۰٬۰۰۰
  بستانکار: سود انباشته ۷۰۰٬۰۰۰
```

**۲ — تسهیم سود** (اختیاری). سود انباشته کاهش و حساب پرداختنی هر شریک
افزایش می‌یابد، بر اساس درصد شراکت.

**۳ — افتتاحیهٔ سال بعد.** فقط مانده‌های **دائمی** منتقل می‌شوند. حساب‌های
موقت منتقل نمی‌شوند چون در گام اول صفر شده‌اند.

### محافظ‌ها

`previewClosing()` پیش از هر تغییری چهار چیز را بررسی می‌کند:

| بررسی | چرا |
|---|---|
| تراز آزمایشی متوازن است | بستن دفتر ناسالم، خطا را دائمی می‌کند |
| سال تمام شده | نمی‌توان سالی را بست که هنوز جریان دارد |
| قبلاً بسته نشده | بستن دوباره سود را دو بار منتقل می‌کند |
| جمع درصد شراکت ≤ ۱۰۰ | وگرنه بیش از سود موجود تسهیم می‌شود |

پس از بستن، دوره **خودکار قفل می‌شود** تا اسناد بسته‌شده تغییر نکنند.

### آزمون‌های کلیدی

سه ادعا که آزمون‌ها ثابت می‌کنند:

```
۱. پس از اختتامیه، مانده هر حساب موقت دقیقاً صفر است
۲. صورت سود و زیان دوره صفر می‌شود
۳. دارایی = بدهی + سرمایه پس از هر سه سند برقرار می‌ماند
```

مورد سوم مهم‌ترین است: اگر بستن سال معادلهٔ حسابداری را بشکند، کل دفتر
بی‌اعتبار می‌شود.

## ۲۲. بررسی سلامت دفتر

`checkIntegrity()` مواردی را می‌گیرد که **نباید هرگز رخ دهند**:

| کد | شدت | معنی |
|---|---|---|
| `unbalanced_entry` | خطا | سند نامتوازن — نقض قاعدهٔ بنیادی |
| `duplicate_entry` | خطا | شناسهٔ تکراری، احتمالاً از همگام‌سازی |
| `unknown_account` | خطا | ارجاع به حسابی که وجود ندارد |
| `incomplete_entry` | خطا | سند کمتر از دو ردیف |
| `negative_amount` | خطا | مبلغ منفی در ردیف |
| `negative_inventory` | هشدار | فروش بیش از موجودی |

تفکیک خطا از هشدار عمدی است: هشدار (مثل موجودی منفی) در مغازه‌های واقعی
رخ می‌دهد و نباید کار را متوقف کند، ولی **خطای جدی مانع بستن سال می‌شود**.

در نرم‌افزار مالی، خطای داده باید پیش از اینکه کاربر متوجه شود پیدا گردد —
نه وقتی که ترازنامه‌اش با اظهارنامه نمی‌خواند.

## ۲۳. مانده اول دوره — باگی که پیدا شد

### علائم

فرم شخص فیلد «مانده اول دوره» داشت، مقدار ذخیره می‌شد، ولی گزارش
بدهکاران صفر نشان می‌داد. مغازه‌داری که با بدهکاری‌های قبلی شروع
می‌کند، آن‌ها را در هیچ گزارشی نمی‌دید.

### ریشه

`postOpening()` در `posting.ts` نوشته و آزمون شده بود، ولی **هیچ‌جا
صدا زده نمی‌شد**. یک تابع درست که به جریان وصل نبود.

```
grep -rn "postOpening" apps/ | wc -l   →  0
```

درس: آزمون واحدِ سبز تضمین نمی‌کند قابلیت به کاربر رسیده باشد. برای
همین آزمون‌های سرتاسری این پروژه از مسیر واقعی `store` عبور می‌کنند،
نه فقط از توابع هسته.

### رفع

`postOpeningBalances()` مانده‌های اشخاص، خزانه و موجودی کالا را جمع
می‌کند و یک سند افتتاحیهٔ متوازن می‌سازد؛ اختلاف به حساب سرمایه می‌رود.

**قابل اجرای مجدد است.** اگر کاربر مانده‌ای را تغییر داد و دوباره ثبت
کرد، سند قبلی حذف و سند جدید ساخته می‌شود:

```ts
const withoutOld = db.entries.filter((e) => e.sourceType !== 'opening');
```

بدون این، هر بار ثبت مبلغ را دو برابر می‌کرد. آزمونی هست که دقیقاً
این را بررسی می‌کند.

## ۲۴. سند دستی

تنها راهی که کاربر مستقیماً به دفتر می‌نویسد. اجازهٔ `entry.manual`
از قبل تعریف شده بود ولی رابطی نداشت.

### چرا اعتبارسنجی سخت‌گیرانه است

سند دستی از محافظت‌های جریان عادی (فاکتور، تراکنش) عبور نمی‌کند، پس
خودش باید محافظ داشته باشد:

| بررسی | دلیل |
|---|---|
| توازن بدهکار و بستانکار | قاعدهٔ بنیادی دفتر |
| حداقل دو ردیف با مبلغ | سند تک‌طرفه بی‌معنی است |
| مبلغ منفی ممنوع | جهت با بدهکار/بستانکار مشخص می‌شود |
| یک ردیف فقط یک طرف | هم‌زمان بدهکار و بستانکار خطای ورودی است |
| رعایت قفل دوره | دورهٔ بسته نباید سند بپذیرد |

رابط کاربری **اختلاف را زنده نشان می‌دهد** و دکمهٔ ثبت تا متوازن نشدن
غیرفعال می‌ماند — خطا پیش از تلاش برای ثبت دیده می‌شود.

### حذف

فقط سند دستی قابل حذف است، آن هم **نرم**. سند خودکار (فاکتور، تراکنش)
با اصلاح منبعش تغییر می‌کند، نه با حذف مستقیم — وگرنه دفتر با فاکتور
ناهماهنگ می‌شود.

## ۲۵. الگوی «تابع درست که وصل نیست»

دو باگ جدی این پروژه یک ریشهٔ مشترک داشتند: تابعی در هسته کاملاً درست
نوشته و آزمون شده بود، ولی **هیچ‌جا صدا زده نمی‌شد**.

```
grep -rn "postOpening"  apps/ | wc -l   →  0    (باگ مانده اول دوره)
grep -rn "createReturn" apps/ | wc -l   →  0    (باگ سود برگشت)
```

هر دو بار آزمون واحد سبز بود. هر دو بار کاربر آسیب می‌دید.

### چرا این الگو خطرناک است

آزمون واحد ثابت می‌کند تابع **درست کار می‌کند**، نه اینکه **به کاربر
رسیده باشد**. بین این دو یک شکاف است که فقط آزمون سرتاسری می‌بیند.

### باگ دوم: سود برگشت فروش

`createReturn()` بهای تمام‌شدهٔ اصلی را به نسبت مقدار برگشتی منتقل
می‌کند. چون وصل نبود، کاربر برگشت را دستی می‌ساخت و مسیر جایگزین در
`store` از **بهای جاری انبار** استفاده می‌کرد.

سناریوی بازتولید:

```
فروش ۵ عدد، بهای واقعی ۱۰۰٬۰۰۰   →  سود ۱٬۰۰۰٬۰۰۰
خرید ۱۰ عدد به ۲۵۰٬۰۰۰            →  بهای جاری بالا رفت
برگشت کامل ۵ عدد
   انتظار: سود ۰
   واقعیت: سود ۵۰۰٬۰۰۰  ← ۵۰۰٬۰۰۰ سود ساختگی
```

هرچه نوسان قیمت خرید بیشتر، خطا بزرگ‌تر. در بازار ایران این نوسان
عادی است، پس باگ در عمل مکرر رخ می‌داد.

### روش تشخیص

پیش از هر دور کار، صادرات هسته با استفادهٔ واقعی مقایسه می‌شود:

```bash
for fn in quoteToSale createReturn buildCorrection historyOf; do
  echo "$fn: $(grep -rn "$fn" apps/*/src | wc -l)"
done
```

صفر بودن یعنی یا قابلیت ناقص است، یا کد مرده. هر دو باید بررسی شوند.

### محافظ‌های دیالوگ برگشت

- مقدار قابل برگشت = مقدار فاکتور منهای آنچه قبلاً برگشت خورده
- ردیف کاملاً برگشت‌خورده غیرفعال می‌شود
- `isFullyReturned()` دکمهٔ برگشت را از فاکتور تمام‌شده برمی‌دارد

بدون اینها، کاربر می‌توانست بیش از مقدار فروخته‌شده برگشت بزند و
موجودی انبار را از واقعیت جدا کند.

## ۲۶. چند کسب‌وکاره

### چرا پایگاه دادهٔ جدا، نه فیلتر؟

دو راه برای multi-tenant وجود داشت:

**الف — یک پایگاه داده، فیلتر با `businessId`.** هر کوئری باید فیلتر
داشته باشد. فراموش کردن یک فیلتر یعنی نشتی داده بین کسب‌وکارها.

**ب — پایگاه دادهٔ جدا برای هر کسب‌وکار.** انتخاب شد.

```
javid:workspaces          فهرست فضاها
javid:db:<business-id>    دادهٔ هر فضا، کاملاً جدا
javid:activeWorkspace     فضای باز
```

با روش ب، نشتی از نظر فیزیکی ممکن نیست — دادهٔ کسب‌وکار دیگر اصلاً
در حافظه بارگذاری نشده. برای برنامه‌ای که روی دستگاه کاربر اجرا
می‌شود و هر فضا حداکثر چند هزار رکورد دارد، این معامله درست است.

`scopeTo()` و `assertScoped()` در هسته برای سمت سرور می‌مانند، جایی
که همهٔ کسب‌وکارها در یک جدول‌اند و فیلتر اجتناب‌ناپذیر است.

### مهاجرت

کاربری که از نسخهٔ تک‌کسب‌وکاره می‌آید نباید کاری انجام دهد:

```ts
await migrateLegacyWorkspace();  // خودکار، هنگام باز شدن برنامه
```

دو محافظ:
- **idempotent** — اگر فهرست خالی نباشد، کاری نمی‌کند
- **دادهٔ قدیمی پاک نمی‌شود** — اگر مهاجرت مشکلی داشت، `javid:db:v1`
  هنوز سر جایش است

این دقیقاً درس شکست مهاجرت رقیب است: مهاجرت دستی که کاربر را وسط راه
بدون دسترسی به دفترش رها می‌کرد.

### خودترمیمی

اگر فهرست بگوید فضایی هست ولی داده‌اش نباشد (مثلاً پاک‌سازی ناقص
مرورگر)، `openActiveWorkspace()` ورودی خراب را حذف و فضای سالم بعدی
را باز می‌کند — به‌جای اینکه برنامه با صفحهٔ سفید بماند.

### حذف با پشتیبان

`deleteWorkspace()` پیش از پاک کردن، محتوای کامل را برمی‌گرداند و
رابط کاربری آن را دانلود می‌کند. حذف بدون راه بازگشت، نقض تعهد اول
است حتی وقتی خود کاربر درخواستش را داده.

## ۲۷. اصلاحیه و ابطالیهٔ صورتحساب

### بن‌بستی که وجود داشت

صفحهٔ سامانهٔ مؤدیان خطاهای سامانه را نمایش می‌داد:

```
⛔ ۰۴۰۰۱۰۱ — امضای دیجیتال معتبر نیست
```

ولی هیچ دکمه‌ای برای اصلاح نبود. کاربر خطا را می‌دید و کاری نمی‌توانست
بکند. `buildCorrection()` در هسته نوشته و آزمون شده بود — همان الگوی
«تابع درست که وصل نیست» برای سومین بار.

### قاعدهٔ سامانه

صورتحساب ارسال‌شده **حذف نمی‌شود**. تنها راه قانونی اصلاح، صدور
صورتحساب جدید با ارجاع به شمارهٔ مالیاتی اصلی است:

| موضوع | کد | کاربرد |
|---|---|---|
| اصلاحی | ۲ | تغییر اقلام یا مبالغ |
| ابطالی | ۳ | معامله انجام نشد |
| برگشت از فروش | ۴ | کالا برگشت خورد |

هر سه در فیلد `irtaxid` به شمارهٔ مالیاتی اصلی ارجاع می‌دهند و
**شمارهٔ مالیاتی جدید** با سریال بعدی می‌گیرند.

### محافظ‌ها

```ts
canCorrect(db, submissionId)
```

- فقط صورتحساب **پذیرفته‌شده** قابل اصلاح است. صورتحسابی که هنوز در
  صف است اصلاً به سامانه نرسیده، پس اصلاحش بی‌معنی است.
- صورتحساب **باطل‌شده** دوباره اصلاح نمی‌شود.
- ابطالیه، وضعیت اصلی را به `cancelled` تغییر می‌دهد تا در فهرست
  روشن باشد کدام صورتحساب دیگر معتبر نیست.

هر اصلاحیه در ردّ ممیزی ثبت می‌شود — چون تغییر یک سند مالیاتی ارسالی
رویدادی است که باید ردیابی شود.

---

## ۲۸. تاریخچهٔ رکورد

`historyOf()` سومین تابع وصل‌نشده بود. حالا دکمهٔ «تاریخچه» روی هر
فاکتور پاسخ می‌دهد: **چه کسی، کِی، چه چیزی را تغییر داد؟**

چون ردّ ممیزی در حالت `update` فقط **تفاوت** را نگه می‌دارد، تاریخچه
دقیقاً نشان می‌دهد کدام فیلدها عوض شده‌اند، نه اینکه کل رکورد را
دوباره چاپ کند.

آزمونی هست که بررسی می‌کند تاریخچهٔ یک رکورد، رویداد رکورد دیگری را
نشان ندهد — همان اصل جداسازی که در چند کسب‌وکاره هم رعایت شد.

---

## ۲۹. تسویهٔ فاکتور — باگی که از زاویهٔ کاربر پیدا شد

سه باگ قبلی با جستجوی «تابع وصل‌نشده» پیدا شدند. این یکی متفاوت بود:
سؤال پرسیدم **«مغازه‌دار چطور فاکتوری را تسویه می‌کند؟»**

### علائم

```
فاکتور ۳۰۰٬۰۰۰ ثبت شد
از صفحهٔ خزانه: دریافت ۳۰۰٬۰۰۰ از همان مشتری
→ پرداخت‌شده: ۰
→ وضعیت: باز
```

پول در صندوق بود، حساب مشتری هم درست تسویه شده بود، ولی **فاکتور
تا ابد باز می‌ماند**.

### ریشه

```ts
export function paidOf(db: DB, invoiceId: ID): Rial {
  return db.transactions
    .filter((t) => t.invoiceId === invoiceId && !t.deletedAt)  // ← هرگز ست نمی‌شد
    .reduce((s, t) => s + t.amount, 0);
}
```

فیلد `invoiceId` در نوع `Transaction` تعریف شده بود، `paidOf` رویش
حساب می‌کرد، ولی هیچ فرمی آن را پر نمی‌کرد. یک زنجیرهٔ ناقص که
TypeScript نمی‌توانست بگیرد چون فیلد اختیاری بود.

### درس

نوع‌های اختیاری (`invoiceId?: ID`) نقطهٔ کوری می‌سازند: کامپایلر
راضی است، ولی منطق روی داده‌ای حساب می‌کند که هرگز نمی‌آید. برای
فیلدهایی که یک محاسبه به آن‌ها وابسته است، باید آزمون سرتاسری
وجود داشته باشد که مسیر کامل را طی کند.

### دو مسیر تسویه

**۱ — تسویهٔ مستقیم.** دکمهٔ «تسویه» روی فاکتور، تراکنش را با
`invoiceId` ثبت می‌کند.

**۲ — تخصیص خودکار.** مشتری مبلغی می‌دهد بدون اشاره به فاکتور خاص —
روش رایج در مغازه. مبلغ از **قدیمی‌ترین** فاکتور باز کم می‌شود و
باقی‌مانده به بعدی می‌رود:

```
فاکتور ۱ (دی):   ۳۰۰٬۰۰۰  →  تسویه کامل
فاکتور ۲ (بهمن): ۳۰۰٬۰۰۰  →  ۱۵۰٬۰۰۰ پرداخت
دریافت ۴۵۰٬۰۰۰
```

مازاد پس از تسویهٔ همهٔ فاکتورها، به صورت **علی‌الحساب** ثبت می‌شود
نه اینکه رد شود — چون در عمل مشتری گاهی بیشتر می‌دهد.

### جهت پرداخت

فاکتور خرید و برگشت از فروش، پرداخت **خروجی**اند نه دریافتی:

```ts
const outgoing = invoice.type === 'purchase' || invoice.type === 'sale_return';
kind: outgoing ? 'pay' : 'receive'
```

بدون این، تسویهٔ فاکتور خرید پول را به صندوق **اضافه** می‌کرد.

## ۳۰. ویرایش فاکتور — جدی‌ترین باگ پروژه

### علائم

```
فاکتور ۳۰۰٬۰۰۰ ثبت شد        →  فروش ۳۰۰٬۰۰۰  ✓
ویرایش: مقدار ۱ → ۲          →  فروش ۹۰۰٬۰۰۰  ✗ (انتظار ۶۰۰٬۰۰۰)
```

هر ویرایش، اثر قبلی را نگه می‌داشت و اثر جدید را رویش می‌گذاشت.

### ریشه

```ts
invoices: [...db.invoices.filter((i) => i.id !== withCosts.id), withCosts],  // ✓ جایگزین
entries:  entry ? [...db.entries, entry] : db.entries,                        // ✗ اضافه
movements: [...db.movements, ...movements],                                   // ✗ اضافه
```

فاکتور **جایگزین** می‌شد ولی سند و حرکت انبار **اضافه**. عدم تقارنی
که در نگاه اول دیده نمی‌شود.

### چرا از همهٔ باگ‌های قبلی بدتر بود

باگ‌های قبلی یک گوشه را خراب می‌کردند. این یکی **همهٔ گزارش‌های مالی**
را هم‌زمان غلط می‌کرد: صورت سود و زیان، ترازنامه، تراز آزمایشی،
موجودی کالا و کاردکس. و چون ویرایش فاکتور کار روزمرهٔ هر مغازه‌دار
است، خطا به‌سرعت انباشته می‌شد.

نکتهٔ ظریف: **ترازنامه همچنان متوازن می‌ماند** چون هر دو سند خودشان
متوازن‌اند. یعنی آزمون «دارایی = بدهی + سرمایه» این باگ را نمی‌گرفت.
فقط مقایسهٔ عدد گزارش با انتظار آن را نشان داد.

### رفع

چون سند و حرکت انبار با `sourceId` به فاکتور گره خورده‌اند، حذف
اثر قبلی امن و دقیق است:

```ts
const staleEntries = existing
  ? db.entries.filter((e) => !(e.sourceType === 'invoice' && e.sourceId === id))
  : db.entries;
```

### حذف فاکتور و محافظ‌ها

`voidInvoice()` اثر مالی و انباری را برمی‌دارد ولی **خود فاکتور را با
پرچم حذف نگه می‌دارد** — ردّ ممیزی نباید سوراخ داشته باشد.

`invoiceEditability()` چهار حالت را می‌بندد:

| وضعیت | چرا قفل |
|---|---|
| پرداخت ثبت‌شده دارد | تراکنش به فاکتور گره خورده |
| به سامانهٔ مؤدیان ارسال شده | باید ابطالیه صادر شود، نه حذف |
| برگشتی دارد | برگشت به بهای این فاکتور وابسته است |
| دورهٔ مالی بسته | اسناد بسته‌شده تغییرناپذیرند |

هر کدام پیام فارسی روشن می‌دهد که کاربر بداند **به‌جایش چه کند**.

## ۳۱. چرخهٔ چک — سه باگ و یک درس معماری

### باگ اصلی: وصول تکراری

```
چک ۱٬۰۰۰٬۰۰۰ ثبت شد
وصول  →  بانک ۱٬۰۰۰٬۰۰۰  ✓
وصول دوباره  →  بانک ۲٬۰۰۰٬۰۰۰  ✗
```

هر بار فشردن دکمه، سند جدید ثبت می‌شد. در عمل با دابل‌کلیک، باز بودن
دو زبانه، یا همگام‌سازی چنددستگاهی رخ می‌داد — و **پول خیالی** در
دفتر می‌ساخت.

مثل باگ ویرایش فاکتور، **ترازنامه متوازن می‌ماند** چون هر سند خودش
متوازن است. این دومین باری بود که آزمون توازن باگ را نگرفت.

### ریشهٔ مشترک هر سه باگ

منطق چک در **کامپوننت رابط کاربری** نوشته شده بود:

```ts
// در Treasury.tsx — خارج از لایهٔ داده
function cashCheque(db, c, event) {
  const entry = postCheque(c, event, treasury, ctxOf(db));
  return { ...next, entries: [...next.entries, entry] };
}
```

چون از `store` عبور نمی‌کرد، سه محافظ موجود را دور می‌زد:
`guardPeriod`، `audit` و بررسی وضعیت. هر قابلیتی که منطق مالی را در
کامپوننت بنویسد، همهٔ محافظ‌های مرکزی را از دست می‌دهد.

**قاعده‌ای که در سند معماری از ابتدا بود:** «اگر یک محاسبهٔ مالی در
`apps/web` نوشتی، احتمالاً جای اشتباهی است.» این باگ دقیقاً نقض
همان قاعده بود.

### ماشین وضعیت صریح

```ts
const CHEQUE_TRANSITIONS: Record<ChequeStatus, ChequeStatus[]> = {
  pending: ['cashed', 'bounced', 'spent', 'void'],
  cashed:  [],            // نهایی
  bounced: ['pending'],   // چک برگشتی می‌تواند دوباره در جریان بیفتد
  spent:   [],
  void:    [],
};
```

به‌جای بررسی‌های پراکندهٔ `if`، جدول انتقال‌های مجاز. هر تلاش
غیرمجاز پیام فارسی روشن می‌دهد:

> چک «وصول شده» را نمی‌توان به «برگشتی» تغییر داد

### یادآوری سررسید

`chequeAlerts()` چک‌های سررسید گذشته و نزدیک را جدا می‌کند و بالای
صفحهٔ خزانه هشدار می‌دهد — قابلیتی که در تحلیل بازار وعده داده شده
بود ولی فقط شمارش می‌شد، نه هشدار.
