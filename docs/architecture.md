## ۱. چرا این معماری؟

هر تصمیم معماری در جاوید پاسخی به یک مشکل مشاهده‌شده در محصولات رقیب است:

| مشاهده در بازار | تصمیم معماری |
|---|---|
| کاربر با پایان اشتراک به دفتر حسابش دسترسی نداشت | ماژول جداگانهٔ `subscription.ts` با فهرست سفید صریح |
| قطعی اینترنت فروش را متوقف می‌کرد | UUID سمت کلاینت + صف تغییرات + ساعت لامپورت |
| چندپلتفرمی شدن به بازنویسی و افت کیفیت انجامید | پکیج `core` بدون هیچ import از DOM یا React |
| گزارش‌ها با واقعیت ناهماهنگ می‌شدند | هیچ جدول تجمیعی ذخیره نمی‌شود |

## ۳. موتور سند دوطرفه

قاعدهٔ تخطی‌ناپذیر: **جمع بدهکار = جمع بستانکار**.

`EntryBuilder` تنها راه ساخت سند است و پیش از تحویل، توازن را بررسی می‌کند:

```ts
const b = new EntryBuilder(bizId, date, 'فروش', 'invoice', invId);
b.debit(receivableId, 1_100_000, { partyId });
b.credit(salesId, 1_000_000);
b.credit(vatPayableId, 100_000);
const entry = b.build(uuid(), now);  // اگر نامتوازن باشد پرتاب می‌کند
```

رفتارهای محافظتی:
- مبلغ صفر → ردیف اضافه نمی‌شود
- مبلغ منفی → خودکار به سمت مقابل منتقل می‌شود
- ردیف با بدهکار و بستانکار هم‌زمان → خطا
- سند تک‌ردیفی → خطا

### الگوهای ثبت

| رویداد | بدهکار | بستانکار |
|---|---|---|
| فروش | دریافتنی | فروش + مالیات فروش |
| بهای فروش | بهای تمام‌شده | موجودی کالا |
| خرید | موجودی + مالیات خرید | پرداختنی |
| برگشت از فروش | برگشت از فروش + مالیات | دریافتنی |
| ↳ بازگشت کالا | موجودی کالا | بهای تمام‌شده |
| دریافت وجه | صندوق/بانک | دریافتنی |
| ثبت چک دریافتی | اسناد دریافتنی | دریافتنی |
| وصول چک | بانک | اسناد دریافتنی |

## ۴. موتور بهای تمام‌شده

سه روش پشتیبانی می‌شود و در سطح کسب‌وکار تنظیم می‌گردد.

```ts
const state = replayProduct(movements, 'fifo');
const { cogs, remaining } = consumeStock(state.layers, 12, 'fifo');
```

- **FIFO** — از قدیمی‌ترین لایه مصرف می‌کند
- **LIFO** — از جدیدترین لایه
- **میانگین موزون** — لایه‌ها در هر ورود ادغام می‌شوند

### ⚠️ تلهٔ برگشت از فروش

باگی که در توسعهٔ جاوید کشف و رفع شد:

> کالای برگشتی باید با **بهای تمام‌شده** به انبار بازگردد، نه با **قیمت فروش**.

اگر با قیمت فروش برگردد، هم ارزش انبار و هم سود دوره متورم می‌شود. مثال:

```
خرید ۱۰۰ عدد × ۱۰٬۰۰۰  →  انبار: ۱٬۰۰۰٬۰۰۰
فروش ۱۲۰ عدد × ۱۵٬۰۰۰  →  بهای فروش: ۱٬۲۴۰٬۰۰۰
برگشت ۲۰ عدد:
  ❌ غلط: انبار +۳۰۰٬۰۰۰ (قیمت فروش)  →  سود متورم
  ✅ درست: انبار +۲۰۰٬۰۰۰ (بهای اصلی) →  سود واقعی
```

`createReturn()` بهای تمام‌شده را به نسبت مقدار برگشتی از فاکتور اصلی منتقل
می‌کند و `invoiceLineUnitCost()` تضمین می‌کند حرکت انبار با بهای درست ثبت شود.
آزمون شمارهٔ ۵ در `scenario.test.ts` این را قفل می‌کند.

## ۵. پول

**قاعده: هیچ‌جا ممیز شناور برای مبلغ استفاده نمی‌شود.** همه‌چیز عدد صحیح ریال است.

```ts
percentOf(100_000, 9)        // ۹٬۰۰۰ — مالیات
mulMoney(1000, 2.5)          // ۲٬۵۰۰ — مقدار می‌تواند اعشاری باشد
allocate(100, [1, 1, 1])     // [۳۴, ۳۳, ۳۳] — جمع دقیقاً ۱۰۰
bankersRound(2.5)            // ۲ — نه ۳
moneyToWords(1_250_000)      // «یک میلیون و دویست و پنجاه هزار ریال»
```

`allocate()` هنگام سرشکن کردن تخفیف کلی بین سطرها استفاده می‌شود و تضمین
می‌کند جمع سهم‌ها **دقیقاً** برابر مبلغ اصلی باشد. آزمون این را روی ده‌ها
ترکیب مبلغ و نسبت بررسی می‌کند.

## ۷. تعهد ۱ — دادهٔ کاربر

`packages/core/src/subscription.ts` عمداً کوچک و صریح نوشته شده:

```ts
export const ALWAYS_ALLOWED = [
  'read', 'search', 'report', 'print',
  'export', 'backup', 'login', 'switch_business', 'renew',
] as const;
```

> این فهرست فقط می‌تواند **بزرگ‌تر** شود. هر تغییری که قابلیتی را از آن
> حذف کند، نقض قولی است که به کاربر داده‌ایم.

چرخهٔ وضعیت:

```
trial / active  ──انقضا──►  grace (۷ روز)  ──►  read_only
   نوشتن ✅                    نوشتن ✅            نوشتن ⛔
   خواندن ✅                   خواندن ✅           خواندن ✅
```

`export.ts` هیچ import از `subscription.ts` ندارد — خروجی گرفتن از نظر فنی
هم به وضعیت اشتراک وابسته نیست.

## ۸. تعهد ۲ — آفلاین

```ts
uuid()                              // شناسه بدون تماس با سرور
clock.tick()                        // ترتیب علّی مستقل از ساعت دستگاه
queue.enqueue({ ... })              // صف تغییرات
queue.compact()                     // چند تغییر روی یک رکورد → آخرین حالت
resolveConflict(local, remote)      // قطعی‌گرا
```

**حل تعارض** سه مرحله دارد و در هر شرایطی روی همهٔ دستگاه‌ها نتیجهٔ یکسان
می‌دهد: ساعت لامپورت → زمان بروزرسانی → شناسهٔ دستگاه (داور قطعی).

لایهٔ ذخیره‌سازی در `apps/web/src/store.ts` با یک آبجکت `storage` انتزاع شده
که در نبود `localStorage` (رندر سمت سرور، حالت خصوصی، سهمیهٔ پر) به حافظهٔ
موقت برمی‌گردد — برنامه هرگز به‌خاطر ذخیره‌سازی از کار نمی‌افتد.

## ۹. آزمون‌ها

```bash
npm test                      # ۸۰ آزمون هسته
```

سه دستهٔ آزمون از بقیه مهم‌ترند:

**`commitments.test.ts`** — نقض تعهدات معماری را می‌گیرد. مثلاً اگر کسی
`export` را پشت اشتراک قفل کند، این آزمون قرمز می‌شود.

**`scenario.test.ts`** — یک مغازهٔ واقعی را شبیه‌سازی می‌کند و پس از
ده‌ها عملیات بررسی می‌کند که تراز آزمایشی متوازن مانده و
دارایی = بدهی + سرمایه برقرار است.

**بررسی رندر** — همهٔ صفحات با داده‌های واقعی سمت سرور رندر می‌شوند:

```bash
cd apps/web
npx vite build --config vite.ssr.config.ts && node ssr-out/render.js
```

این کار خطاهای زمان اجرا را پیش از رسیدن به کاربر می‌گیرد و بررسی می‌کند
که در حالت فقط-خواندنی، دکمهٔ ثبت پنهان ولی دکمهٔ خروجی فعال باشد.

## ۱۰. افزودن قابلیت جدید

۱. **نوع را در `types.ts` تعریف کن**
۲. **اگر اثر مالی دارد، الگوی ثبت را در `posting.ts` بنویس** — هرگز جای دیگری سند نساز
۳. **گزارش را در `reports.ts` از دفتر مشتق کن** — هیچ مانده‌ای ذخیره نکن
۴. **آزمون بنویس** — حداقل یکی که توازن سند را بررسی کند
۵. **رابط کاربری را در `apps/web` اضافه کن** — هیچ منطق مالی در کامپوننت نگذار

قاعدهٔ کلی: اگر یک محاسبهٔ مالی در `apps/web` نوشتی، احتمالاً جای اشتباهی است.
