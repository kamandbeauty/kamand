## چرا جاوید؟

جاوید پس از بررسی دقیق بازار اپلیکیشن‌های حسابداری موبایل ایران ساخته شد. مطالعهٔ رقبا و
مهم‌تر از آن **شکایت‌های واقعی کاربرانشان**، سه مشکل تکرارشونده را نشان داد:

| مشکل رایج در بازار | پاسخ جاوید |
|---|---|
| با پایان اشتراک، دسترسی به دفتر حساب مشتریان قطع می‌شود | **دادهٔ شما هرگز گروگان گرفته نمی‌شود** |
| وابستگی کامل به سرور؛ قطعی اینترنت یعنی توقف فروش | **آفلاین-اول** |
| چندپلتفرمی شدن با بازنویسی از صفر و افت کیفیت | **منطق دامنه مستقل از رابط کاربری** |

این سه، نه «قابلیت» بلکه **تعهد معماری** هستند و در کد قفل شده‌اند
(`subscription.ts`، `sync.ts` و جدایی پکیج `core`). آزمون‌های
[`commitments.test.ts`](packages/core/test/commitments.test.ts) نقض آن‌ها را
به صورت خودکار می‌گیرند.

## تعهد اول: دادهٔ شما متعلق به شماست

بزرگ‌ترین شکایت کاربران نرم‌افزارهای مشابه این است که با تمام شدن اشتراک،
به اطلاعات **خودشان** دسترسی ندارند. در جاوید:

```
پس از انقضای اشتراک:
  ✅ مشاهده، جستجو، گزارش‌گیری، چاپ، خروجی Excel/JSON  →  همیشه آزاد
  ⛔ فقط ثبت رکورد جدید                                  →  قفل
```

به‌علاوه: هشدار در ۱۴، ۷، ۳ و ۱ روز مانده به انقضا، و **۷ روز مهلت ارفاق** پس از آن.
دکمهٔ «دریافت کل اطلاعات» در تنظیمات، بدون هیچ شرطی همیشه فعال است.

## تعهد دوم: بدون اینترنت هم کار می‌کند

مغازه‌دار وسط فروش نباید با قطعی اینترنت متوقف شود.

- همهٔ نوشتن‌ها ابتدا **محلی** ذخیره می‌شوند
- شناسه‌ها **UUID سمت کلاینت** هستند تا رکورد بدون تماس با سرور ساخته شود
- **ساعت لامپورت** ترتیب علّی رویدادها را مستقل از ساعت دستگاه حفظ می‌کند
- حل تعارض **قطعی‌گرا** است: نتیجه روی همهٔ دستگاه‌ها یکسان درمی‌آید

## تعهد سوم: هسته مستقل از رابط کاربری

پکیج `@javid/core` هیچ وابستگی‌ای به مرورگر، React یا پایگاه داده ندارد.
همان هسته می‌تواند پشت وب، موبایل یا دسکتاپ بنشیند — بدون بازنویسی.

## معماری

```
packages/core/          هستهٔ حسابداری — بدون وابستگی به UI
  money.ts              پول صحیح (ریال)، گرد کردن بانکی، مبلغ به حروف
  jalali.ts             تقویم جلالی بدون کتابخانهٔ خارجی
  ledger.ts             ⭐ موتور سند دوطرفه — تضمین توازن
  inventory.ts          ⭐ بهای تمام‌شده: FIFO / LIFO / میانگین موزون
  invoice.ts            محاسبات فاکتور و اعتبارسنجی
  posting.ts            تبدیل رویداد کسب‌وکار به سند متوازن
  reports.ts            نُه گزارش، همه مشتق از دفتر
  subscription.ts       🔒 تعهد ۱
  sync.ts               🔒 تعهد ۲
  export.ts             خروجی CSV / Excel / پشتیبان کامل

apps/web/               رابط کاربری React + Vite
```

### اصول طراحی

**۱ — پول هرگز اعشاری نیست.** همهٔ مبالغ عدد صحیح ریال هستند. گرد کردن
نیم-زوج (banker's rounding) از سوگیری انباشته جلوگیری می‌کند، و `allocate()`
تضمین می‌کند هنگام سرشکن کردن تخفیف **حتی یک ریال گم نشود**.

**۲ — هیچ گزارشی ذخیره نمی‌شود.** همهٔ گزارش‌ها در لحظه از `JournalEntry` و
`StockMovement` مشتق می‌شوند. نتیجه: گزارش هرگز با واقعیت ناهماهنگ نمی‌شود.

**۳ — سند نامتوازن وارد دفتر نمی‌شود.** `EntryBuilder` پیش از ساخت هر سند،
توازن را بررسی می‌کند و در صورت نقض `UnbalancedEntryError` پرتاب می‌کند.

**۴ — تاریخ میلادی ذخیره، شمسی نمایش.** داده به ISO ذخیره می‌شود و فقط در
لحظهٔ نمایش به جلالی تبدیل می‌گردد.

## آزمون‌ها

```
پول و گرد کردن            ۹    سرشکن کردن بدون گم شدن ریال
تاریخ جلالی               ۷    رفت‌وبرگشت پایدار ۱۳۹۵–۱۴۱۰
سند دوطرفه                ۴    رد کردن سند نامتوازن
فاکتور                    ۷    تخفیف، مالیات، اعتبارسنجی
موجودی                    ۵    FIFO / LIFO / میانگین
ثبت و گزارش               ۸    توازن همهٔ انواع سند
تعهدات معماری            ۱۹    ⭐ قفل بودن تعهد ۱ و ۲
خروجی داده                ۵    CSV، Excel، پشتیبان
سناریوی واقعی مغازه      ۱۴    ⭐ توازن پس از ده‌ها عملیات
────────────────────────────
جمع                      ۸۰
```

مهم‌ترین آزمون‌ها دو مورد هستند: پس از یک سناریوی کامل (خرید، خرید دوم،
فروش، دریافت وجه، برگشت)، **تراز آزمایشی باید متوازن بماند** و
**دارایی = بدهی + سرمایه** برقرار باشد. اگر روزی موتور حسابداری بشکند،
این دو آزمون اولین کسانی هستند که خبر می‌دهند.
